# REST API интернет-магазина — дизайн MVP

## Цель

Создать REST API интернет-магазина на FastAPI и PostgreSQL. Пользователь может зарегистрироваться, войти, просматривать опубликованный каталог, управлять своей корзиной и оформить заказ. Администратор управляет категориями и товарами.

## Границы MVP

В MVP входят:

- регистрация и вход по email и паролю;
- access JWT без refresh-токенов;
- роли `customer` и `admin`;
- публичный просмотр категорий и опубликованных товаров;
- административное управление каталогом;
- одна активная корзина на пользователя;
- оформление заказа с проверкой и списанием остатков;
- просмотр пользователем только собственных заказов.

В MVP не входят платёжные интеграции, доставка, промокоды, отзывы, возвраты, резервирование остатков и восстановление остатков после отмены заказа.

## Архитектура

Приложение представляет собой модульный монолит. Оно запускается как один FastAPI-сервис, но разделено на модули с явными границами:

- `auth` — регистрация, вход, JWT и определение текущего пользователя;
- `users` — пользователь, роль и активность;
- `catalog` — категории и товары;
- `cart` — активная корзина и её позиции;
- `orders` — оформление и чтение заказов;
- `core` — конфигурация, база данных, безопасность и общие ошибки.

В каждом бизнес-модуле HTTP-роутеры отвечают только за транспорт и валидацию, сервисы содержат бизнес-правила, а репозитории инкапсулируют SQLAlchemy-запросы. Модули взаимодействуют через сервисные интерфейсы и модели данных, не обращаясь к чужим роутерам.

Технологический набор:

- Python и FastAPI;
- PostgreSQL;
- SQLAlchemy 2.0 с асинхронными сессиями;
- Alembic для миграций;
- Pydantic для входных и выходных схем;
- Argon2 для хеширования паролей;
- JWT access-токены;
- pytest, Ruff и mypy;
- Dockerfile и Docker Compose.

## Модель данных

### Пользователи

`users` содержит:

- `id`;
- уникальный нормализованный `email`;
- `password_hash`;
- `role`: `customer` или `admin`;
- `is_active`;
- даты создания и обновления.

Публичная регистрация всегда создаёт роль `customer`. Администратор создаётся отдельной CLI-командой.

### Каталог

`categories` содержит `id`, уникальный `slug`, название и даты создания и обновления.

`products` содержит:

- `id`;
- ссылку на категорию;
- уникальный `slug`;
- название и описание;
- цену `numeric` с двумя десятичными знаками;
- неотрицательный `stock_quantity`;
- `is_published`;
- даты создания и обновления.

Административное удаление товара выполняется мягко: товар снимается с публикации. Это сохраняет целостность истории заказов. Удаление категории с привязанными товарами запрещено.

### Корзина

`carts` содержит `id`, пользователя и даты создания и обновления. Для каждого пользователя существует не более одной активной корзины.

`cart_items` содержит корзину, товар и положительное количество. Пара `(cart_id, product_id)` уникальна. Цена в корзине не фиксируется: актуальная цена вычисляется по данным товара.

### Заказы

`orders` содержит:

- `id`;
- пользователя;
- статус `created`;
- итоговую сумму;
- дату создания.

Изменение статуса, отмена и возврат товара не входят в MVP.

`order_items` содержит:

- ссылку на заказ;
- идентификатор исходного товара;
- снимок названия товара;
- снимок цены за единицу;
- количество;
- сумму позиции.

Снимок делает заказ независимым от будущих изменений каталога.

## HTTP API

Все пути имеют префикс `/api/v1`.

### Авторизация

- `POST /auth/register` — регистрация customer;
- `POST /auth/login` — получение bearer access JWT;
- `GET /auth/me` — данные текущего пользователя.

### Категории

- `GET /categories` — публичный список;
- `POST /categories` — создание администратором;
- `PATCH /categories/{category_id}` — изменение администратором;
- `DELETE /categories/{category_id}` — удаление пустой категории администратором.

### Товары

- `GET /products` — опубликованные товары с пагинацией и фильтром по категории;
- `GET /products/{product_id}` — опубликованный товар;
- `POST /products` — создание администратором;
- `PATCH /products/{product_id}` — изменение администратором;
- `DELETE /products/{product_id}` — снятие с публикации администратором.

Пагинация использует `limit` и `offset`; значения по умолчанию — 20 и 0, максимальный `limit` — 100.

### Корзина

- `GET /cart` — текущая корзина;
- `POST /cart/items` — добавить товар или увеличить количество существующей позиции;
- `PATCH /cart/items/{item_id}` — установить количество;
- `DELETE /cart/items/{item_id}` — удалить позицию.

Добавление и изменение позиции запрещает количество выше текущего остатка. Окончательная проверка всегда повторяется при checkout.

### Заказы

- `POST /orders/checkout` — оформить текущую корзину;
- `GET /orders` — список собственных заказов;
- `GET /orders/{order_id}` — собственный заказ.

Пользователь не может читать чужие корзины или заказы.

## Оформление заказа

Checkout выполняется в одной транзакции PostgreSQL:

1. Сервер загружает непустую корзину пользователя.
2. Строки всех участвующих товаров блокируются в стабильном порядке через `SELECT ... FOR UPDATE`.
3. Сервер проверяет публикацию товаров и достаточность каждого остатка.
4. Цена каждой позиции повторно читается из базы.
5. Сервер рассчитывает суммы позиций и итог с использованием `Decimal`.
6. Создаются заказ и неизменяемые позиции заказа.
7. Остатки уменьшаются.
8. Позиции корзины удаляются.
9. Транзакция фиксируется.

При любой ошибке вся операция откатывается. Это предотвращает частично созданные заказы и продажу сверх остатка при конкурентных запросах.

## Безопасность

- Пароли хешируются Argon2 и никогда не возвращаются API.
- JWT подписывается секретом из окружения и содержит идентификатор пользователя, роль, время выдачи и срок действия.
- Срок жизни access-токена конфигурируется; значение по умолчанию — 30 минут.
- Неактивный пользователь не может войти или обращаться к защищённым эндпоинтам.
- Проверка роли admin выполняется централизованной FastAPI-зависимостью.
- Цена, итог и роль пользователя никогда не принимаются от клиента как доверенные значения.

## Ошибки

Ошибки имеют единый формат:

```json
{
  "error": {
    "code": "insufficient_stock",
    "message": "Недостаточно товара на складе",
    "details": {}
  }
}
```

Используются:

- `400` — нарушено бизнес-правило, например пустая корзина;
- `401` — отсутствующий или некорректный JWT;
- `403` — недостаточная роль;
- `404` — сущность недоступна или не принадлежит пользователю;
- `409` — конфликт уникальности или недостаточный остаток;
- `422` — ошибка валидации запроса.

Внутренние исключения и детали базы данных клиенту не раскрываются.

## Тестирование и качество

Модульные тесты проверяют сервисные правила без HTTP. Интеграционные тесты работают с PostgreSQL и проверяют репозитории, транзакционный checkout и конкурентное списание остатков. API-тесты покрывают:

- регистрацию, вход и доступ к `/auth/me`;
- запрет повышения роли через регистрацию;
- публичное чтение каталога;
- административные права на изменение каталога;
- изоляцию корзин и заказов пользователей;
- изменение позиций корзины;
- успешный checkout;
- пустую корзину, скрытый товар и недостаточный остаток;
- неизменность заказа после изменения товара.

Команды проверки запускают Ruff, mypy и pytest. CI выполняет эти проверки на каждый push и pull request.

## Критерии готовности

MVP готов, когда:

1. Новый пользователь регистрируется, входит и получает доступ к своему профилю.
2. Пользователь видит опубликованные категории и товары.
3. Администратор создаёт, изменяет и скрывает каталог.
4. Пользователь добавляет доступные товары в свою корзину и меняет их количество.
5. Checkout атомарно создаёт заказ, списывает остаток и очищает корзину.
6. Пользователь видит только собственные заказы.
7. Конкурентные checkout не могут списать больше имеющегося остатка.
8. Миграции, линтинг, типизация и тесты проходят в документированном окружении.
